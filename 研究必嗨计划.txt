3. 必嗨弱点：扩展什么，面试最响

比 Kafka 更贴必嗨，改动可控，before/after 最好做。

② 第二选：Kafka（或 NATS JetStream）削峰 — 聊天室→接入
chatroom → Kafka topic(rid 分区) → 消费者按 nid 批量 push → websocket
解决	说明
chatroom 与 fan-out 解耦
峰值弹幕不拖死 RTMQ worker
可 replay / 审计
运营公告、对账
对比 PDF 弹幕架构
面试官爱听
注意：demo 可 单 broker；面试强调 热路径异步化，不是吹百万 QPS。

③ 第三选：websocket 批量 fan-out
TravRoomSession 改为 batch 写 / writev / 合并 WS 帧
指标：1w 连接同房 的 fan-out 耗时（配合 64G 压 500～2000 真连接 外推）
④ 第四选：限流 + 背压（产品级）
房间/用户 QPS 限制、优先级队列（系统 BC > 用户 chat）
偏 平台完整性，性能数字可能不如 ①② 显眼
⑤ 不建议作为第一个改造
换整个 RTMQ → 太大
仅加 Redis Cluster → 运维故事多，性能故事弱
敏感词 → 产品项，不是性能项

「异步 ACK + 内存队列广播，ingress QPS 提升 X 倍；引入 Kafka 解耦 chatroom 与接入层，削峰填谷，并补充 Prometheus 与 K8s HPA。」
