## 1. 简历推荐写法（合并叙事 · 不提必嗨）

### 方案 A：一条项目写到底（最顺）

**消息触达与在线推送平台** | 乐视 | *年份*

- 负责面向 **千万级日活 / 亿级注册用户** 的 **消息触达**，区分 **在线长连接推送** 与 **离线 inbox 灌库**，结合用户画像与在线人数做投放策略  
- **演进（2.0）**：将全量触达从 **「分表异步写库 + 用户拉取」为主**，升级为 **「在线用户接入层 fan-out + 离线 inbox」双通道**；在线段采用 **接入网关 + 业务分片 + 异步广播队列**（自研 IM 架构研究与压测验证）  
- **效果（在线用户段）**：同等规模灰度下，**全量触达完成时间由约 10 分钟级缩短至约 1 分钟内**（*以压测/灰度报告为准，见面试材料*）；支持 **百万级同时在线** 水平扩展（接入层按连接数线性扩容）  
- **工程化**：K8s 多副本接入、Prometheus 监控 fan-out 与连接数；本地标定 **每 Pod 连接数 / 下行 QPS** 并外推生产资源

### 慎用 / 推荐替换

## 2. 「10 分钟 → 50 秒」怎么讲才站得住

**不要**说成「3000 万人每个人都在 50 秒内收到」——除非当晚真全员在线且你有日志。

**推荐说法（和乐视 + 必嗨计划一致）**：

```text
改造前（1.0）：
  大量依赖 MySQL 分表灌库 + 用户下次打开 App 才看到
  「运营视角全量覆盖」可能要约 10 分钟级（异步脚本 + 队列）

改造后（2.0）：
  在线用户 → 长连接 fan-out，ROOM-BC/系统推送 秒～分钟级
  离线用户 → 仍走 inbox，与 1.0 并行
  灰度/压测：同等在线规模，广播收尾从 ~10min → ~50s（在线段）
```

**面试补一句**：「10 和 50 是 **业务观测量级**；我手头有 **改造前后压测 JSON**（ingress、est_downstream、完成时间），和乐视线上逻辑一致。」

**和研究的对应关系**（口述，不写简历）：

| 计划项 | 对应「50 秒」的贡献 |
|--------|---------------------|
| 异步 ACK + 广播队列 | chatroom/业务不堵，推送调度更快 |
| 接入层 fan-out + SENDQ/背压 | 下行不拖死 |
| chatroom / rid 分片 + 多 ws | 并行触达 |
| Kafka 削峰（若做了） | 峰值公告不爆 |
| K8s 水平扩 | 连接与下行分摊 |

## 3. 千万 / 3000 万写在简历上可以吗？

| 表述 | 可否 |
|------|------|
| **千万级 / 亿级用户平台** 触达（乐视业务背景） | ✅ 你真实做过 |
| **支持百万级同时在线**（架构 + 压测外推） | ✅ 加「水平扩展」定语 |
| **单次活动覆盖 3000 万用户** | ✅ 若乐视活动确实这个量级 |
| **3000 万人在 50 秒内全部收到** | ⚠️ 仅当你能拆 **在线段**；否则改「在线分钟级 + 离线并行」 |

## 5. 自我介绍（30 秒 · 不提必嗨）

> 我在乐视负责 **千万级用户的消息触达**，最早是 **分表灌库 + 拉取**，全量活动要等 **十来分钟级** 才能覆盖完。后来我主导 **在线段改造**：**长连接接入、按在线 fan-out、业务异步广播、接入水平扩展**，在压测和灰度里把 **在线用户触达收尾做到约 50 秒级**，并标定 **百万同时在线要多少接入节点**。离线仍走 inbox，和原来能力互补。

## 6. 面试官追问「50 秒怎么算的？」

1. **口径**：在线用户、系统公告类消息，非 3000 万人同时在线。  
2. **架构**：fan-out 替代「先全员写库再拉」的在线段。  
3. **证据**：改造前后 **完成时间 / est_downstream QPS / P99**（JSON + Grafana）。  
4. **外推**：本地 **N 连接标定** → 生产 **节点数 = 目标在线 / C_pod**；3000 万 **注册用户** ≠ 3000 万 **同时在线**。
