## 2. 三分钟口述稿（可直接背）

> **背景**：乐视全站播放等行为日志，量级大约 **一天一亿条** 播放埋点，要驱动 **用户积分和成长等级** 更新。硬性要求是：**同一个用户的记录不能多 goroutine、多进程并发算**，否则积分连续计算会脏写、等级错乱。
>
> **方案**：全部行为先进 **Kafka**。Producer 发送时用 **user_id 做 hash 选 partition**，这样同一用户永远落在同一分区；消费组里 **一个分区同一时刻只绑一个 consumer 进程**，进程内 **每个 partition 单独一个 goroutine 串行拉取**，从根上保证同用户顺序处理。这是业界标准做法，比 Master 转发消息更稳。
>
> **架构上分两层**：**Consumer Worker** 干活——Go 批量 fetch、批内按 user 聚合、算分、写 **Redis** 做热数据，再 **异步批量刷 MySQL** 落地等级；批量 commit offset 保吞吐。**Master** 只做管控——注册心跳、规则热更、堆积监控、死信重放，**不消费业务消息**，避免单点瓶颈。
>
> **容量**：按日一亿、峰值按均值约 30 倍估，峰值 QPS 大约 **3.5 万**；单 Go 进程稳态大约 **1.2～1.5 万 QPS**，**16 个 partition、4 台 Worker** 留冗余，峰值能盖住还有余量。失败走重试，仍失败进 **DLQ**，Master 侧重放排查。
>
> **效果口径**：等级是 **近实时/准实时**——进 Kafka 后 **秒到分钟级** 反映到 Redis/库，不是毫秒级；日级 **上亿条** 行为可稳定消费。和后面我在必嗨方向二里 **Kafka key=rid 同房有序** 是同一套 **分片有序 + 无状态 Worker 扩** 的思路。

**时长**：正常语速约 **2.5～3 分钟**；若面试官打断，优先保留 **加粗句**。

## 3. 白板图（30 秒）

```text
埋点 → Kafka Producer(key=user_id)
           ↓
    Topic · 16 partitions
    （同 user → 同 partition → 有序）
           ↓
    Consumer Group · Go Worker × 4
    每 partition · 1 goroutine 串行
           ↓
    批量 fetch → groupByUserID → 算积分/等级
           ↓
    Redis（热） ──异步批量──→ MySQL（落地）
           ↓
    batch commit offset · 失败 → DLQ

Master（主备）：监控 / 配置 / DLQ 工具 · 不拉业务消息
```

## 4. 五条追问 · 参考答法

### Q1：为什么必须保证「同用户不并发」？能不能加锁而不是分区？

**答**：

- 等级/积分是 **读-改-写** 连续状态，并发会丢更新或顺序乱序，最终等级和积分不一致。
- **分区串行** 从消息入口保证顺序，Consumer 逻辑简单，无需分布式锁，也无锁超时、死锁、Redis 锁续期问题。
- 跨分区用户本来就在不同 key 上，互不影响；同用户 hash 到同分区即可。

**加分一句**：和 IM 里「同房 rid 进同一 Kafka partition」是同一类 **按 key 有序** 问题。

---

### Q2：分区数 16 怎么来的？流量涨怎么扩？

**答**：

- 日 **1 亿** → 平均约 **1157 QPS**；短视频晚高峰按 **~30 倍** 估峰值约 **3.5 万 QPS**（可按线上监控校准）。
- 单 partition Go 批量消费稳态约 **3000～5000 QPS**，取 **4000** 估 → 理论最少 **~9** 分区；工程上取 **16** 留扩容和 rebalance 余量。
- 扩容：**增加 partition**（需规划 rebalance）+ **增加 Consumer Worker**；Worker **无状态**，Kafka 重分配 partition 即可。
- **注意**：partition 只增不减；扩 partition 后老 key 不会迁移，新 partition 只接新 hash 范围——要讲清楚这是 Kafka 常规约束。

---

### Q3：Master 干什么？为什么不用 Master 统一拉消息再分给 Worker？（方案 B）

**答**：

- **方案 B**（Master 消费全部分区再 RPC 转发）会在 Master 形成 **3 万+ QPS 单点**，延迟多一跳，Master 挂全链路停——生产 **否决**。
- **方案 A（实际采用）**：Kafka **原生 partition 分配** 做负载均衡；Master 只做 **控制面**：配置下发、堆积/延迟监控、DLQ 重放、扩缩容策略，**不参与消息转发**。
- 元数据可用 **etcd** 等做 Master 主备，Master 挂了消费仍继续，只是暂时少管控。

---

### Q4：Redis 和 MySQL 怎么分工？为什么不一笔行为写一次库？

**答**：

- 一亿/日若直写 MySQL，即使用户分散，峰值仍会把库打满；积分还是 **高频读**（展示等级）+ **高频写**（每条行为）。
- **Redis Hash** 存当前积分/成长值/等级，Consumer 算完先写缓存，查询走 Redis。
- **MySQL** 做权威落地：按 **批量大小或时间窗口** 异步刷盘，降低 DB TPS；故障可从 Redis/日志补偿（需说明你们当时的补偿策略）。
- 面试诚实：**近实时** = 缓存秒级可见，库可能 **略滞后**，业务上要接受或做双读策略。

---

### Q5：和你在做的必嗨 / IM 有什么关系？

**答**（IM 岗专用）：

- **不同业务**：等级是 **行为 pipeline**；必嗨是 **IM 信令与消息**。
- **相同架构模式**：
  - Kafka **按 key 分区有序**（user_id vs rid）；
  - **无状态 Consumer 水平扩**（等级 Worker vs 方向二 roomfanout）；
  - 热路径 **异步化**，避免同步拖垮核心服务（等级不阻塞播放上报；弹幕 chatroom 受理后进 Kafka）。
- **乐视触达** 则补 **在线 fan-out + 长连接**，三条线组成：**触达规模 + 行为 Kafka + IM RTMQ**。

## 5. 简历 bullet（可直接贴乐视块）

```text
用户等级异步计算体系（Golang + Kafka）：
  播放等行为日亿级入 Kafka；Producer 按 user_id hash 分区，Consumer 组内单 partition
  串行消费，保证同用户积分/等级连续计算无并发脏写；Redis 热数据 + MySQL 批量落库；
  Master 管控面负责监控堆积、规则热更与 DLQ 重放（不参与消息转发）。支撑等级准实时更新。
```

**数字口径**：日 **上亿条** 行为（与简历一致）；**近实时** 说 **秒～分钟级**，不说毫秒。

## 6. 诚实边界（背下来，防追问穿帮）

| 可以说 | 慎说 / 需确认本人参与度 |
|--------|-------------------------|
| 日亿级行为、按 user 分区、Go Consumer、Redis+MySQL | Master+etcd 是否全量上线 |
| 同用户串行、Consumer 无状态扩展 | 精确 QPS 数字是否来自监控 |
| 近实时（秒～分钟） | 「近实时」= 非强一致实时 |
| 方案 B 否决、DLQ、批量 commit | 压测报告 / topic 名 / 分区数（备好一个真实例子） |

**若 Master 当时只做监控、规则配置较简**：说「**消费链路我先落地，管控面与平台组迭代**」，不要夸大。
