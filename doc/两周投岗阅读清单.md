### Day 8～9：RTMQ 概念（不啃源码）

| 读 | 深度 |
|----|------|

**5 分钟口述模板**：

> RTMQ 是必嗨自研的 **进程间 TCP 消息总线**。各服务连 frwder 的 FORWARD 或 BACKEND 端口；**publish** 按 cmd 投给订阅者，**async_send** 按 nid 投给指定接入节点。Go 和 C 共用同一套协议，所以 frwder 用 C、业务用 Go 可以混搭。

## 附录 A：core 4 天出彩套餐 + 面试金句

> **适用**：路径 B 网关/中间件向；路径 A 可选 **Day 1（iovec+mref）** 防 C 追问。  
> **原则**：讲 **工业界经典原理**（nginx/内核同类），不吹「必嗨比 Kafka 强」。  
> **总量**：精读约 **~2500 行**，跳过 core 其余 ~8000+ 行。

### 和流行方案怎么比（一句话）

| 必嗨 core | 当下常见 | 面试口径 |
|-----------|----------|----------|
| wiov + writev | nginx、网关批量发 | 「减少 syscall、缓解 TCP 小包」 |
| mref 引用计数 | sk_buff、Netty retain、shared_ptr | 「异步多阶段共享包，防 use-after-free」 |
| slab（源自 nginx） | tcmalloc 小对象 | 「小块固定槽位，减 malloc 碎片」 |
| pthread 线程池 | Go 协程、Tokio | 「经典 one-queue worker，够用」 |
| AVL 订阅表 | 哈希 / std::map | 「rtmq 按 cmd 查订阅，O(log n) 可接受」 |
| 自研 shm | mmap 环、Kafka | 「进程间低延迟队列；业务持久化仍靠 Redis/Mongo」 |

**勿夸大**：仓库 **无 io_uring**；实际是 **epoll 时代 + pthread**（简历勿写 io_uring 除非另学）。

### Day 1：批量发包 `iovec.c` + access 用法

| 读 | 路径 | 关注函数 |
|----|------|----------|
| wiov 封装 | `src/clang/lib/core/iovec.c` | `wiov_init`、`wiov_add`（若有）、`wiov_clean`、`wiov_item_adjust` |
| 接入层发包 | `src/clang/lib/access/acc_rsvr.c` | 搜 `writev`、`wiov`、`iovec` |

**验证**：grep 确认谁调 wiov：`rg "wiov_" src/clang/lib/access src/clang/exec/listend`

**面试金句**：

1. 「下行 fan-out 时多段 header+body 用 **writev 聚合成一次 syscall**，避免循环 send 的小包风暴。」  
2. 「`wiov_clean` 在发送失败时按段回调释放，避免半发送状态下内存泄漏。」  
3. 「Linux `IOV_MAX` 1024，所以 wiov 有上限，超大 fan-out 要分批。」

**若被追问「和 io_uring 比」**：「writev 是同步批量写；io_uring 是异步提交，原理都是 **少 syscall**；必嗨这代是 epoll+writev。」

---

### Day 2：包生命周期 `mref.c` + rtmq 引用点

| 读 | 路径 | 关注 |
|----|------|------|
| 引用计数 | `src/clang/lib/core/mref.c` | `mref_add`、`mref_get`、`mref_put`、全局 `hash_tab` |
| 谁在用 | `src/clang/lib/rtmq/server/rtmq_recv.c` | 搜 `mref_` |
| 对照 | `src/clang/exec/frwder/frwder.c` | 启动时 `mref_init()` |

**面试金句**：

1. 「RTMQ 收包后可能经 **worker 线程异步处理**，用 mref 保证 buffer 在最后一个消费者 release 前不被 free。」  
2. 「类似内核 **sk_buff 引用计数** 或 Netty **retain/release**，只是 C 手写。」  
3. 「和 shared_ptr 区别：按 **裸指针地址** 做 hash 表管理，更贴近 C 风格。」

**若被追问「为何不用 shared_ptr」**：「全栈 C + Go 混编，C 侧用统一 mref 协议；Go 侧有自己的 GC。」

---

### Day 3：TCP 基础 `sck_tcp.c` + `redo.c`

| 读 | 路径 | 关注 |
|----|------|------|
| 监听/连接 | `src/clang/lib/core/sck_tcp.c` | `tcp_listen`、非阻塞设置、**LINGER 注释块** |
| 安全 IO | `src/clang/lib/core/redo.c` | `Open`、`Read`、`Write` 遇 EINTR 重试 |

**面试金句**：

1. 「接入层 **listen 后设 non-blocking + SO_REUSEADDR**，accept/read 配合 epoll（access 层）。」  
2. 「**LINGER=0** 可避 TIME_WAIT，但可能 RST 丢数据；生产一般谨慎开。」  
3. 「**redo 封装 EINTR 重试**，是成熟 C 网络服务的标配，nginx 同类。」

**若被追问 TIME_WAIT**：「主动关闭方等待 2MSL；高并发短连接要 **连接复用 / 客户端重连**，不是无限开 LINGER=0。」

---

### Day 4：内存 + 订阅结构 `slab.c` + `avl_tree.c` + rtmq

| 读 | 路径 | 关注 |
|----|------|------|
| 小对象分配 | `src/clang/lib/core/slab.c` | 文件头注释（**来自 nginx**）；`slab_alloc` 思路 |
| 内存池 | `src/clang/lib/core/mem_pool.c` | 扫 `mem_pool_alloc`（可选 30min） |
| AVL API | `src/clang/lib/core/avl_tree.c` | `avl_creat`、`avl_insert`、`avl_query`、`avl_trav` |
| rtmq 用法 | `src/clang/lib/rtmq/server/rtmq_recv.c` | 搜 `avl_creat`、`avl_query`、`ctx->reg` |
| 订阅组 | `src/clang/lib/rtmq/server/rtmq_comm.c` | `list->groups` 与 avl |

**面试金句**：

1. 「**slab 适合小于 4K 的小对象**，和 nginx 一样按页切槽；大块仍走系统分配。」  
2. 「RTMQ **Register(cmd)** 存在 **avl 注册表**，publish 时按 cmd 找订阅者，类似主题路由。」  
3. 「订阅组用 avl 管理 **同一 cmd 下多个订阅 socket**；遍历组内节点做 fan-out。」

**若被追问「为何 AVL 不用哈希」**：「cmd 数量可控、需有序遍历；哈希 O(1) 也行，这是实现选择，不是性能极限。」
