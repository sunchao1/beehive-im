优信 - 银行金融客户材料高性能文件传输系统 技术设计文档
文档概述
1. 项目背景
   优信二手车业务产生海量车贷客户档案：身份证、征信、购车合同、车辆高清扫描件、分期申请表，文件混合海量小图 + 数十 MB 级 PDF 大图，每日万级客户批量推送至多家合作银行前置网关。
   原有商用 SFTP 工具存在并发低、大文件 IO 卡顿、无断点续传、审计日志缺失、高峰期丢包对账困难等问题。
   自研C++ 高性能文件传输后台服务，承担企业侧文件封装、分片、可靠传输、校验、重试、日志审计，对接银行金融文件网关，满足金融等保、数据安全、高吞吐性能要求。
2. 核心业务约束
   文件特征：混合小文件 (几十 KB 图片) + 超大扫描件 (10~50MB PDF)，批量打包推送；
   性能要求：无 GC 停顿、低内存开销、高并发吞吐、专线带宽可控；
   金融强制规范：文件 MD5 完整性校验、全链路操作留痕可对账、内外网隔离、禁止与银行 P2P 直连传输；
   可靠性：断点续传、失败自动重试、磁盘队列削峰、文件防篡改、传输状态持久化。
3. 是否使用 Qt？分场景结论
   后端核心传输服务：完全不需要 Qt
   后台是 Linux 服务程序，无 GUI，纯 C++ 标准库 + 系统调用 (epoll/mmap/sendfile)、第三方网络 / 压缩库，Qt 仅带界面组件，服务端引入只会增加依赖包、内存开销，生产环境不使用。
   可选配套场景才会用到 Qt（非核心链路）
   内部运维管理客户端：Windows 运维桌面程序，供运营查看传输任务、手动重发、文件校验、对账查询 → 可用 Qt 开发 GUI；
   本地离线文件预处理工具：业务部门本地批量压缩、加密文件桌面小工具；
   架构划分建议：传输核心服务纯 C++ 无 Qt，运维客户端可选 Qt，两者解耦独立部署
   一、系统整体架构（分层设计）
1. 整体拓扑（金融隔离架构，无 P2P）
   业务应用集群（优信内网）
   ↓ 内网访问
   文件预处理 & 传输调度服务（C++ 核心服务，部署 DMZ 隔离区）
   ↓ 单向专线 / 加密通道
   多家银行前置网关（SFTP / 金融标准文件接口）
   关键约束：仅我方主动向外推送，银行侧无法主动访问我方内网，不搭建两端 P2P 直连通道，符合银行安全规范。
2. 四层分层架构
   接入层：接收业务系统 HTTP / 消息队列任务（Kafka/RabbitMQ），接收待传输客户档案任务；
   预处理层：文件遍历、批量压缩、分片切割、全局 MD5 / 分片 MD5 计算、敏感文件校验；
   高性能传输内核层（C++ 核心）：异步网络、零拷贝 IO、可靠分片传输、断点续传、限流削峰；
   审计持久层：传输任务落盘、全链路日志、对账数据入库、异常告警推送。
3. 模块拆分
   任务调度模块
   文件 IO 内核模块（mmap/sendfile 零拷贝）
   分片 / 合并模块
   压缩加密模块
   异步网络传输模块（epoll Reactor）
   磁盘消息队列削峰模块
   校验与重试模块
   日志审计 & 告警模块
   运维管控接口（HTTP 接口，供后台管理页面调用）
   【可选】Qt 运维桌面客户端（独立项目，不侵入传输服务）
   二、核心技术栈明细
   后端传输服务（无 Qt，Linux C++）
   语言标准：C++17
   网络模型：epoll 多 Reactor 异步 IO，自研 TCP 可靠传输协议（替代原生 SFTP 低效协议）
   文件高性能 IO：Linux 系统调用 mmap、sendfile 零拷贝，减少用户态 / 内核态切换
   序列化：Protobuf 传输任务、分片元数据
   压缩：zstd（图片 / PDF 批量高压缩比，降低专线带宽消耗）
   加密：OpenSSL 文件 AES 加密、传输链路 TLS
   本地持久化：LevelDB 存储传输任务、分片进度（实现断点续传）
   消息队列对接：librdkafka（接收业务推送任务）
   日志：spdlog 高性能异步落盘日志（满足金融审计）
   监控告警：prometheus-cpp 埋点，对接告警平台
   HTTP 管控接口：muduo /nghttp2 轻量化 http 服务，供运营后台调用
   可选配套：Qt 运维客户端（独立桌面程序，不参与传输链路）
   Qt 6.5 + QWidget / QML
   功能：任务列表查询、失败任务手动重发、文件 MD5 校验工具、传输流量监控看板、本地批量文件预处理
   部署：仅运营办公 Windows 电脑安装，不部署机房服务器
   存储依赖
   本地磁盘：原始客户文件、分片缓存、任务持久化 LevelDB
   MySQL：每日对账汇总数据、历史传输记录归档
   中间件依赖
   RabbitMQ/Kafka：业务侧下发文件传输任务
   Prometheus + Grafana：系统性能监控
   三、核心模块详细设计
   3.1 任务调度模块
   业务系统推送客户档案传输任务（客户 ID、文件路径列表、目标银行标识、优先级）；
   调度器分优先级队列：高优贷款加急件、普通批量档案；
   流量控制：按银行专线配置最大并发传输数，防止打满带宽；
   削峰机制：瞬时海量任务写入本地 LevelDB 磁盘队列，异步消费，避免内存溢出。
   3.2 文件 IO 内核（解决大文件 / 海量小文件性能痛点）
   超大 PDF 扫描件：使用 mmap 映射文件到内存，无缓冲区拷贝；
   文件网络发送：sendfile 直接内核转发至 socket，零拷贝；
   海量小文件优化：批量打包成压缩包后统一传输，减少网络连接次数；
   文件资源池：复用文件句柄、缓冲区，减少频繁打开关闭文件的系统开销。
   3.3 分片与可靠传输模块
   分片规则：单文件超过 10MB 自动分片，分片大小可配置；
   每分片携带：分片序号、文件全局 MD5、分片 MD5、客户唯一标识；
   传输协议设计：自定义 TCP 报文头，TLS 加密链路，心跳保活；
   断点续传逻辑：
   每成功传输一个分片，将进度持久化至 LevelDB；
   服务重启 / 网络中断后，重启任务仅重传未完成分片，无需全文件重传；
   接收端（银行网关侧）全部分片接收完成后，合并完整文件，校验全局 MD5，校验通过才标记传输成功。
   3.4 压缩加密模块
   批量图片、PDF 使用 zstd 预压缩后传输，平均降低 60% 传输体积；
   本地落地客户原始文件 AES 加密存储，防止内部数据泄露；
   与银行通信链路全程 TLS 1.3 加密。
   3.5 重试与异常处理
   分片传输超时、丢包、校验失败自动重试，阶梯退避策略；
   达到最大重试次数标记任务失败，写入审计日志并触发告警；
   区分异常类型：网络断连、银行网关拒绝、文件损坏、权限不足，分类告警。
   3.6 审计日志模块（金融核心要求）
   每条传输记录永久留存，包含字段：
   客户 ID、银行渠道、文件名称、文件大小、全局 MD5、传输起止时间、分片数量、传输状态、操作人、机器节点、耗时；
   日志异步落盘，支持按客户 / 日期 / 银行渠道检索对账，满足监管审计。
   3.7 Qt 运维客户端（独立附属系统，非必需）
   适用场景
   机房无外网、运营人员需要本地桌面工具排查传输异常，不依赖网页后台。
   核心功能
   HTTP 调用服务管控接口，展示实时传输任务、失败列表；
   本地工具：批量计算文件 MD5、批量压缩客户档案；
   流量可视化看板，展示各银行专线实时吞吐；
   手动触发失败任务重传、任务取消；
   关键说明
   该 Qt 程序仅做展示、本地预处理、操作下发，不承担任何文件传输逻辑，文件收发依旧由 Linux C++ 服务完成，两者通过 HTTP 接口交互，完全解耦。
   四、性能优化方案（简历 & 面试重点）
   IO 优化：mmap+sendfile 零拷贝，消除用户态缓冲区拷贝；
   网络优化：epoll 多 Reactor 模型，单进程上万并发连接；
   内存优化：C++ 手动内存管理，无 GC 停顿，缓冲区池化复用；
   批量优化：海量小文件打包压缩传输，减少 TCP 握手次数；
   削峰优化：磁盘 LevelDB 队列，高峰流量不丢失任务；
   带宽优化：动态压缩 + 分流通量控制，多银行专线带宽隔离互不抢占。
   五、安全与合规设计（对接银行硬性要求）
   网络隔离：传输服务部署 DMZ 区，仅主动向外发起连接，禁止外部主动入站；
   无 P2P 直连：所有文件走我方中转服务推送银行前置，不建立企业两端点对点通道；
   文件完整性：双层 MD5 校验（分片 + 全文件），防止传输篡改；
   全链路审计：所有操作日志持久化，支持监管对账追溯；
   传输加密：链路 TLS1.3，本地存储文件 AES 加密；
   访问管控：管控接口做身份鉴权，限制仅内网运维访问。
   六、部署方案
   核心传输服务：Linux CentOS，后台常驻 C++ 程序，无 GUI，无 Qt 依赖；
   运维 Web 后台：独立 Java/Go Web 项目；
   Qt 桌面客户端：可选，仅运营办公 Windows 电脑本地安装，不部署服务器；
   集群扩容：支持多节点分布式部署，任务分片分发，横向提升吞吐。
   七、Qt 使用总结（关键结论，面试直接回答）
   核心文件传输后台服务：不引入 Qt
   Qt 是 GUI 框架，附带大量窗口、界面依赖，Linux 服务程序不需要图形组件，引入会增加编译依赖、运行内存、镜像体积，线上生产环境完全弃用 Qt；
   Qt 仅作为可选配套桌面工具
   仅内部运营本地客户端使用，负责查询、本地文件预处理、任务操作，不参与底层文件收发传输逻辑，和核心 C++ 服务通过 HTTP 接口解耦；
