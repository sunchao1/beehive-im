# 百万用户弹幕演示 · 反向容量与一日云成本

> **目标**：演示时用 **最少机器 + 可测数据**，讲清 **「百万 IM 弹幕量级」** 如何成立（实测 + 线性外推，不造假）。  
> **前提**：软件侧 **该扩扩**（chatroom 分片、异步 ACK、Kafka 削峰、ws batch、慢连接隔离）；**机器不省**，但 **演示时长只买 1 天**。

---

## 1. 先定「百万」三种口径（演示必须选一种讲）

| 口径 | 含义 | 能否 1 天真连 | 推荐演示方式 |
|------|------|---------------|--------------|
| **A. 百万在线连接** | 100 万条 WS/TCP 同时在线 | 贵（见 §6） | **测 1～3 万真连接 + 曲线外推** |
| **B. 百万同时收一条公告** | 100 万用户在 **可接受 SLA** 内收到同一条系统消息 | 可以 | **1000 rid × 1000 人 + 并行 ROOM-BC** |
| **C. 百万级热房弹幕** | 单房 **十万～百万观众** + 高频弹幕 | 全量 fan-out 不现实 | **真连 1～2 万 + 合并/采样 + 外推** |

**面试推荐主口径**：**B + A 的外推**（最贴你乐视触达 + 必嗨 fan-out 故事）。  
**C** 必须说明：业界单房百万在线 **不会对每条弹幕做 100 万次全量 push**（客户端合并、档位、采样）。

---

## 2. 核心公式（倒退机器数都用它）

```text
总下行 fan-out/s  �  Σ (每房 ingress_qps × 该房在线人数)

单 Pod websocket 可持续 fan-out  ≈  batch 优化后 5k～20k/s（16C32G，待压测标定）
单 Pod chatroom ingress（异步 ACK + Kafka）≈  200～800/s（待压测标定）

所需 websocket Pod 数  ≈  峰值总下行 / 单 Pod fan-out 能力
所需 chatroom Pod 数   ≈  峰值总 ingress / 单 Pod ingress 能力
```

**连接数**（与 QPS 独立）：

```text
每 Pod 长连接（Go ws，调优后）≈  5k～15k
100 万连接  ≈  1000000 / 10000 ≈  100 个 websocket Pod（仅连接，不含 fan-out 峰值）
```

## 3. 软件改造清单（演示前必做，否则机器白堆）

| 优先级 | 改造 | 作用 |
|--------|------|------|
| P0 | chatroom **异步 ACK** + 广播队列 | 拉高 ingress，worker 不堵 |
| P0 | chatroom **按 rid 分片**（一致性哈希 → 多 Deployment） | 水平扩 ingress |
| P0 | Kafka（或 NATS）**chatroom → 接入** 削峰 | 峰值不拖死 chatroom |
| P0 | websocket **batch 写**（合并帧 / 批量 sendq） | 单 Pod fan-out ×3～10 |
| P1 | **慢连接隔离**（sendq 满 drop + 单独 slow 队列） | P99 不被拖死 |
| P1 | ROOM-BC **只推本房相关 nid**（修 push 扫全集群） | 省无效 RTMQ |
| P1 | loadtest **1 发 N 看** + **多 rid 并行** | 可测 B 口径 |
| P2 | 超大房 **客户端合并/采样**（demo 可配置） | C 口径才讲得通 |

## 4. 演示方案 B：100 万用户收公告（**推荐主方案**）

### 4.1 模型

- **1000 个 rid**，每房 **1000 在线** = **100 万连接**
- 运营发 **同一条系统消息**：对每个 rid 调一次 `POST /room/push`（ROOM-BC）
- 每房下行 = **1000 次 WS 推送**（1 条 BC × 1000 人）
- **总下行峰值**（若 1000 房 **同一秒** push）：**100 万条**
- **若 60 秒内滚动 push 完 1000 房**：平均 **≈ 1.67 万条/s**，峰值看并行度

### 4.2 机器倒退（优化后假设，**需压测标定**）

假设标定后：

- websocket Pod（16C32G，batch 后）：**10k fan-out/s** 可持续
- 每 Pod 连接：**10k** 长连接

| 资源 | 计算 | 数量 |
|------|------|------|
| websocket | 100 万连接 / 1 万/Pod | **100 Pod**（或 **50 Pod × 2 万连接** 激进） |
| 并行 push 峰值 100 万下行/s | 1e6 / 10k | **100 Pod**（与上合并） |
| 60s 滚动 push | 1.67 万/s / 10k | **2～4 Pod** 即可（**演示省钱用滚动 push**） |
| chatroom | 1000 次 HTTP/s 峰值 + Kafka | **3～5 Pod** |
| Kafka | 3 broker | **3 Pod** |
| frwder | 2 | **2 Pod** |
| Redis | 16C 或云 Redis 8G | **1～3** |
| MySQL/Mongo | 2 | **2** |
| 压测/控制 | loadtest 驱动 1000 push | **2×16C** |

**演示省钱配置（真连接可略少，靠压测补故事）**：

| 策略 | 真 WS 连接 | ws Pod | 说明 |
|------|------------|--------|------|
| **省钱演示** | **2～3 万**（20～30 房 × 1000 人） | **15～20** | 其余 **700+ 房用数学外推** |
| **标准演示** | **10 万** | **40～50** | 100 房 × 1000 人实测 + 外推 |
| **满血 1 天** | **100 万真连接** | **80～120** | 见 §6 成本 |

**收齐 100 万用户时间（ROOM-BC，滚动 push 1000 房）**：

- 并行 **50 房/秒** × 每房 fan-out 1s → **~20 秒～2 分钟** 发完 1000 房（取决于单房 1000 推送耗时）
- 用户感知：**半分钟～3 分钟** 全平台可见（**秒级～分钟级**，不是几小时 MySQL 灌库）

## 5. 演示方案 C：热房弹幕「百万观众量级」

### 5.1 现实约束

单房 **100 万在线**，**500 ingress/s** 弹幕，若 **每条全量 fan-out**：

```text
500 × 1000000 = 5 亿 下行/s  →  不可能在一日 demo 集群实现
```

**必须**至少其一：

- **采样/合并**：服务端每 100ms 合并为一个包；或只推最近 N 条  
- **分 gid**（必嗨已有 1 万/组）：100 万 = 100 个 gid，ingress 按组 fan-out  
- **演示**：真连 **1～2 万** 观众，ingress **200/s**，实测 **200 × 2万 = 400 万/s** 仍太高 → 需 **batch + 多 ws** 或 **降低演示 ingress**

### 5.2 可测的「百万叙事」热房 demo

| 参数 | 值 |
|------|-----|
| 真连接 | **20,000**（2 万） |
| ingress | **200/s**（压测） |
| 总下行 | **400 万/s** |
| ws Pod（10k/s each） | **400** Pod → **太贵** |

**改 ingress 为 20/s**（更贴真实人均）：

- 下行 = 20 × 20000 = **40 万/s**
- ws Pod @ 10k/s → **40 Pod** + batch

**演示话术**：「2 万真连接、20/s ingress、40 万/s 下行；线性外推 100 万观众同 ingress 密度需 **2000 ws Pod** 或 **采样降 fan-out**——与线上一致。」

## 6. 一日云成本估算（人民币，按量 ~24h）

> 单价按国内主流云 **按需 16C32G ≈ ¥1.0～2.0/小时**、**32C64G ≈ ¥2.5～4.0/小时**；**抢占式/spot 约 3～5 折**。带宽 **¥0.8～1.2/GB** 出网另计。

### 方案 ① 省钱演示（推荐面试）

**目标**：3 万真连接 + 30 房 × 1000 人 ROOM-BC + 异步 ACK/Kafka/batch **已上**

| 资源 | 规格 × 数量 | 24h 费用（按需） | spot 约 |
|------|-------------|------------------|---------|
| websocket | 16C32G × **18** | ¥860～1700 | ¥400～900 |
| chatroom | 8C16G × **4** | ¥200～400 | ¥100～200 |
| frwder+业务 | 8C16G × **4** | ¥200～400 | ¥100～200 |
| Kafka | 4C8G × **3** | ¥150～300 | ¥80～150 |
| Redis 云 | 8G 主从 | ¥200～500 | — |
| DB | 4C8G × **2** | ¥100～200 | — |
| 压测机 | 16C32G × **2** | ¥100～200 | — |
| 带宽 | 500GB～2TB | ¥400～2000 | — |
| **合计** | | **¥2200～5700** | **¥1200～3000** |

**呈现**：Grafana **3 万连接、ingress、总下行、扩缩容** + 一页 PPT **线性外推到 100 万**。

## 7. 为什么之前说「ingress 只有几十」——扩完机器后应是多少

| 阶段 | 单房 ingress | 1000 房 aggregate ingress | 说明 |
|------|--------------|---------------------------|------|
| 现网 demo（同步 ACK，1 chatroom） | **~40** | 40（单房） | 已测 |
| + 异步 ACK | **200～500** / chatroom Pod | | 待测 |
| chatroom **10 Pod** 分片 | | **2000～5000/s** | 多 rid 并行 |
| + Kafka 解耦 | 峰值写入 Kafka **1 万+/s** | lag 可控 | 削峰 |

**5×16C ws 之前预测低**，是因为 **只扩 ws、没扩 chatroom、没 batch、场景是 1 发 N 看（ingress=发送者人数）**。  
**扩满后**应看 **aggregate 下行** 和 **多 rid 并行**，不是单房 ingress。

## 8. 演示当天流程（15～30 分钟给面试官）

1. 架构图：**rid → chatroom 分片 → Kafka → ws 多副本 → fan-out**  
2. Grafana：当前 **连接数、ingress、总下行 = ingress×N、Kafka lag**  
3. 触发 **30 房 × 1000 人 ROOM-BC**（或 100 房）  
4. `kubectl scale websocket 15 → 30`，再压一次，**P99/drop 下降**  
5. 一页表：**3 万连接实测 → 100 万 = ×33 节点（或 spot 约 ¥X/天）**
